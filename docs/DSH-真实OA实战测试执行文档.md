## 0. 给测试执行者的话

### 0.1 你的角色

你是**测试者**，不是开发者。你的职责是：

- ✅ 按流程录制、回放、观察、记录
- ✅ 如实报告失败与异常
- ✅ 人工核对自动生成的产物是否正确
- ❌ **不修改 `packages/` 下任何代码**
- ❌ **不修改 Mock OA 的前端或后端代码**
- ❌ **不修改任何测试用例的断言**

发现问题只记录，不修复。修复是下一轮开发任务。

### 0.2 三条铁律

**① 不许为了让测试通过而改 OA**

这个项目已经踩过两次：Mock 最初用静态 id 导致测试全绿但结论作废；Mock 会话 cookie 太麻烦于是加了 `maxAge`，把真实困难从测试环境里删掉了。

**如果某个控件定位不了，那是 DSH 的问题，不是 OA 的问题。** 如实记录，不要动 OA。

**② HTTP 200 不等于业务正确**

所有提交类操作，**必须查询服务端实际记录的数据**再判定成功。

已经出过一次事故：参数绑错导致"申请周末加班、实际提交工作日加班"，全流程返回 200 零报错。**只看状态码会漏掉整类静默错单。**

**③ 报告要区分「实测」「推断」「未验证」**

不确定的写不确定。查不到的写查不到。**不要为了让报告完整而推测后当作结论。**

### 0.3 本次测试要回答的核心问题

不是"能不能跑通"，而是这四个：

| # | 问题 | 关键指标 |
|---|---|---|
| Q1 | 技能能活多久？ | **network 步骤占比**（越高越不怕前端改版） |
| Q2 | 定位有多稳？ | **HIGH / LOW 占比**、rebuild 后是否还能回放 |
| Q3 | 参数识别准不准？ | 人工核对每个参数的绑定是否正确 |
| Q4 | 多录制策略可行吗？ | 同一表单不同变体各录一次，能否正确区分 |

**跑通只是及格线。上面四个指标才是这次测试的产出。**

## 1. Phase 0 · 前置核实【必须先做完】

这四项不做完，后面的测试结果不可信。

### 0-A · 补跑全量 e2e

T-86~T-89 修改的是**分析器**（draft 生成、请求关联），那是所有下游的上游。但该轮只跑了 31 个定向 e2e，而完整套件有 89 个。

```bash
npm run e2e          # 或仓库中对应的全量命令
```

**记录**：passed / failed / skipped，以及每个 skipped 的原因。

**判定**：
- 全部通过 → 继续
- 有失败 → **停止**，报告失败项，不要进入 Phase 1

### 0-B · 解释测试数量变化

T-83 报告：`T68-T74 + T84: 25 passed`
T-86~T-90 报告：`T68-T74 + T84: 21 passed`

**少了 4 个测试，未说明原因。** 查明属于哪种：

- 测试被合并或重命名，grep 模式没匹配上 → 列出合并前后的对应关系
- 测试被移除 → 列出被移除的测试名与移除原因
- 测试被 skip 但未计入 skipped → **这是问题**，如实报告

### 0-C · A3 rebuild 循环【本项目最核心的验收】

整个项目的立项前提是"Vue 每次 build 元素都变"。但 A3 一直在 skipped 里，**从未在完整链路上验证过**。

```
循环 5 次：
  1. 记录当前页面某个按钮的 class 名
  2. 重新 build 前端
  3. 断言 class 名已变化（若没变，说明 build 配置有问题，记录并停止）
  4. 用已有技能 dsh replay
  5. 断言回放成功
```

**记录**：每轮的 class 变化前后、回放结果、失败原因。

**判定**：5 轮全过 → 通过；任一轮失败 → 记录失败细节，**但不阻塞后续 Phase**（这是重要发现，不是环境问题）。

### 0-D · OA 代表性审计

在 OA 的加班申请页 F12 Console 执行：

```js
(() => {
  const r = {};
  // 1. hash 化的 class 数量
  r.hashClass = [...document.querySelectorAll('[class]')]
    .filter(e => typeof e.className === 'string' && /_\w+_\w{5,}/.test(e.className)).length;
  // 2. scoped style 属性
  r.scopedAttr = [...document.querySelectorAll('*')]
    .filter(e => [...e.attributes].some(a => /^data-v-/.test(a.name))).length;
  // 3. 静态手写 id（排除组件库动态生成的）
  r.staticId = [...document.querySelectorAll('[id]')]
    .filter(e => !/-[a-z0-9]{6,}$/.test(e.id)).length;
  // 4. label 是否有 for 关联
  const labels = [...document.querySelectorAll('label')];
  r.labelTotal = labels.length;
  r.labelWithFor = labels.filter(l => l.getAttribute('for')).length;
  // 5. append-to-body 的浮层
  r.portaledPanels = [...document.body.children]
    .filter(e => typeof e.className === 'string'
      && /dropdown|picker|popper|overlay|dialog/i.test(e.className)).length;
  // 6. 无可访问名的按钮
  const btns = [...document.querySelectorAll('button,[role=button]')];
  r.btnTotal = btns.length;
  r.btnNoName = btns.filter(b => !b.textContent.trim() && !b.getAttribute('aria-label')).length;
  // 7. 表单控件总数
  r.formControls = document.querySelectorAll(
    'input,textarea,select,.el-select,.el-date-editor').length;
  return r;
})();
```

**判读标准**：

| 指标 | 像真实内网系统 | 像"为测试而写" |
|---|---|---|
| `hashClass` | 大量（> 10） | 0 |
| `scopedAttr` | 大量 | 0 |
| `staticId` | 接近 0 | 大量 |
| **`labelWithFor / labelTotal`** | **接近 0** | **接近 1** |
| `portaledPanels` | > 0 | 0 |
| `btnNoName` | 有一些（图标按钮） | 0 |

**`labelWithFor` 那条最关键**：Element Plus 的 `el-form-item__label` 天生没有 `for` 属性。如果 OA 里 label 都规规矩矩带 `for`，说明它不是标准 Element 用法，定位难度会比真实系统低一个量级。

**判定**：
- 三项以上偏向左列 → OA 具备代表性，继续
- 三项以上偏向右列 → **报告结论，等人工裁决**，不要自行修改 OA

## 4. Phase 3 · 联动流程（加班）

同 Phase 2 流程，但重点验证**联动依赖**。

### 4.1 录制与分析

```bash
dsh record --entry <entry-id> --out ./tmp/t2-overtime
dsh analyze ./tmp/t2-overtime --out ./skills/t2_overtime.draft.yaml
```

操作时**必须触发联动**（选择加班类型后带出审批人或类似字段）。

### 4.2 联动专项核对

- [ ] 联动请求被捕获了吗？
- [ ] 它被关联到了**正确的动作**吗？（应该是"选择类型"，不是后面的填写动作）
- [ ] `_correlation.method` 是什么？（期望 `request-value-match` 或 `dom-causality`，若为 `time-window` 且 `confidence: low`，记录）
- [ ] submit 步骤有没有正确引用联动响应的值？形如 `{{sN.xxx}}`
- [ ] **有没有把联动返回的动态值硬编码？**

### 4.3 跨参数回放【本阶段最关键】

```
1. 录制时用类型 A
2. 回放时传类型 B
3. 观察：是否重新调用了联动接口
4. 查服务端：记录的类型和审批人是不是 B 对应的
```

**判定**：
- 成功且服务端数据正确 → PASS
- 被服务端拒绝（如审批人不匹配）→ 依赖链有问题，记录详情
- **成功但服务端记录的是类型 A → 严重问题，立即报告**

### 4.4 慢节奏录制对比

再录一次，但**每个操作之间停顿 2 秒以上**（模拟真人操作节奏）。

- [ ] 联动请求的归属是否仍然正确？
- [ ] `_correlation` 的 method 和 confidence 有无变化？

### 5.3 交叉测试【重点】

## 7. Phase 6 · 会话中断

### 7.1 回放中途会话过期

```
1. 开始回放一个多步技能
2. 在中途手动使会话失效（清 cookie / 调用后端登出接口）
3. 观察
```

**记录**：

- [ ] 是否检测到会话失效？
- [ ] 是否弹出登录提示（前台横幅）？
- [ ] 重新登录后是否从**锚点重跑**（而不是从断点继续）？
- [ ] 提交数量是否仍为 1？（不能因为重跑而重复提交）

### 7.2 换身份恢复

```
1. 同上，中途使会话失效
2. 用**另一个账号**登录
3. 观察
```

**期望**：中止执行，报身份不一致，**不得继续**。

### 7.3 录制中途会话过期

```
1. 开始录制，操作几步
2. 使会话失效
3. 继续操作（会跳登录页）
4. 观察
```

**期望**：
- [ ] 立即停止记录
- [ ] 已录部分保留
- [ ] **登录页上的点击不得出现在 record.json 中**
- [ ] 提示用户重新登录

## 10. 严重度分级标准

报告问题时按此分级：

| 级别 | 定义 | 例子 |
|---|---|---|
| **P0 静默错误** | 执行成功、无报错，但业务数据错误 | 传周末加班实际提交工作日；缺字段但仍提交成功 |
| **P0 重复副作用** | 同一操作产生多条业务记录 | 提交数量 > 1 |
| **P1 定位漂移未拦截** | LOW 步骤指向了错误控件但未被 T-84 拦住 | |
| **P1 会话/身份问题** | 换身份后继续执行；登录动作被录进技能 | |
| **P2 失败但可发现** | 回放失败并明确报错 | 定位不到、断言失败 |
| **P3 体验问题** | 需要过多人工修正、报错信息不清晰 | |

**P0 类问题一旦发现，立即在报告开头单独列出，不要埋在明细里。**
