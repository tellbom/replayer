## P0-1 · 新增 `postcondition` 契约

### 问题

v1.1 的 T-39 要求：`outcome_unknown` 时"先运行可用 postcondition/assertion 判断业务是否其实成功"。

但 `SkillSchema` 中只有 `assertions`，而 assertions 全部是对 submit **响应**做断言（`httpStatus` / `jsonPath` / `textPresent` / `regexExtract`）。`drop_response=1` 场景下响应根本不存在，这些断言无从执行。

结果：T-39 的第 2、3 步是死代码，每次 `outcome_unknown` 都只能抛错中止。安全语义成立，但"能确认成功则转 confirmed_success"这条分支永远走不到，验收也测不出真实价值。

### 变更 1.1 — `packages/core/src/schema.ts` 新增

```ts
/**
 * 幂等后置查询：用于在响应丢失（outcome_unknown）时，
 * 通过独立的只读查询确认业务副作用是否已经产生。
 * 必须是 GET 且幂等，执行任意次都不得改变业务状态。
 */
export const PostconditionSchema = z.object({
  // 只允许 GET，防止后置查询本身产生副作用
  request: z.object({
    method: z.literal('GET'),
    url: z.string(),
    headers: z.record(z.string()).optional(),
  }),
  match: z.object({
    // 从响应中取出候选集合，例 "$.list[*]"
    jsonPath: z.string(),
    // 候选项需同时满足的字段条件，值支持模板
    // 例 { reason: "{{reason}}", startTime: "{{startTime}}" }
    where: z.record(z.string()),
    // 可选：只在最近 N 条中查找，避免历史数据误判
    limit: z.number().optional(),
  }),
  // true = 找到即视为业务已成功；false = 找不到才算成功
  expectFound: z.boolean().default(true),
  timeoutMs: z.number().default(10_000),
});

export type Postcondition = z.infer<typeof PostconditionSchema>;
```

在 `SkillSchema` 中，与 `assertions` 平级新增：

```ts
export const SkillSchema = z.object({
  // ... skill / auth / params / preflight / steps 不变
  assertions: z.array(AssertionSchema).default([]),

  /** 【v1.2 新增】响应丢失时用于确认业务结果的幂等查询 */
  postcondition: PostconditionSchema.optional(),

  // ... _healHistory / _notes 不变
});
```

### 变更 1.2 — `Step` 级可选覆盖

多数技能只需技能级 postcondition。但当一个技能含多个写步骤时，需要步骤级：

```ts
export const StepSchema = z.object({
  // ... 原有字段不变
  /** 【v1.2 新增】步骤级 postcondition，优先于技能级 */
  postcondition: PostconditionSchema.optional(),
});
```

**解析优先级**：`step.postcondition` → `skill.postcondition` → 无（则 `outcome_unknown` 直接中止）。

### 变更 1.3 — T-05 Mock 需支持后置查询

在 v1.1 的 T-05 交付基础上追加：

- `GET /api/overtime/history?limit=&order=desc` 必须返回**本 session 已创建的真实申请**（不能只是静态假数据），字段至少含 `no / type / startTime / endTime / reason / createdAt`
- 与 K9 虚拟滚动用的 200 条假数据分开：假数据用于 UI 展示，真实提交记录必须能被查到
- `GET /api/_debug/submissions` 保留，仅作测试断言用，**不得**被 postcondition 引用（postcondition 必须走真实业务查询接口，否则内网迁移无对应物）

**追加验收**：
```bash
# 提交一条 → history 能查到
curl -X POST .../api/overtime/submit -d '{...,"reason":"版本上线"}'
curl -s '.../api/overtime/history?limit=5' | grep '版本上线'
```

### 变更 1.4 — T-33 draft 生成器需产出 postcondition 草稿

在 v1.1 的 T-33 基础上追加：

- 若录制过程中出现过"提交后跳转到列表页 / 调用了历史查询接口"，把该 GET 请求作为 postcondition 的 `request` 候选
- `match.where` 用参数化字段自动填充（从 T-31 的参数候选中取业务标识字段，如 reason、startTime）
- **整段打 `# TODO`**，注明"请确认此查询能唯一定位本次提交"
- 若无法推断，写入注释：
  ```yaml
  # TODO: 未能自动推断 postcondition。
  # 缺少 postcondition 时，一旦提交响应丢失，回放将直接中止并要求人工判断。
  # 强烈建议手工补一个幂等的 GET 查询。
  # postcondition:
  #   request: { method: GET, url: /api/xxx/history?limit=5 }
  #   match: { jsonPath: "$.list[*]", where: { reason: "{{reason}}" } }
  #   expectFound: true
  ```

### 变更 1.5 — T-39 postcondition 执行逻辑

替换 v1.1 T-39 中 `outcome_unknown` 分支的描述为：

```
outcome_unknown 处理流程（严格按序，不得跳步）：

1. 禁止任何自动 UI fallback / network retry
2. 解析 postcondition：step.postcondition → skill.postcondition
   ├─ 不存在 → 直接抛 OutcomeUnknownError + 诊断包 + 中止
   └─ 存在 → 继续
3. 执行 postcondition（页面上下文内 GET，遵守 C2）
   ├─ 请求本身失败 → 抛 OutcomeUnknownError + 中止
   └─ 成功 → 继续
4. 按 match.jsonPath 取候选集，按 match.where（模板解析后）逐项匹配
   ├─ 命中 && expectFound=true  → outcome 改写为 confirmed_success，继续后续步骤
   ├─ 未命中 && expectFound=true → outcome 改写为 confirmed_failure，
   │                                此时才允许按安全重试规则降级
   └─ 其余组合按 expectFound 语义对称处理
5. 无论走哪条分支，都必须在 StepResult 中记录
   { outcomeResolvedBy: 'postcondition', postconditionResult: ... }
   并写入诊断包
```

**硬约束**：postcondition 只能是 GET。若 YAML 中写了非 GET，`parseSkill()` 直接校验失败（由 `z.literal('GET')` 保证）。

### 变更 1.6 — T-52 安全专项验收升级

替换 v1.1 中 S1 的描述：

```
S1-a 无 postcondition 场景：
  drop_response=1 → 抛 OutcomeUnknownError 中止
  → /api/_debug/submissions 数量 == 1（服务端已创建，客户端未重复提交）

S1-b 有 postcondition 场景：
  drop_response=1 → 自动执行 postcondition 查到该条
  → outcome 改写为 confirmed_success
  → 回放继续/正常结束
  → /api/_debug/submissions 数量 == 1（关键：没有因为"确认成功"而再提交一次）

S1-c postcondition 查不到场景：
  构造一个提交前即失败的场景（如 approvalToken 失效）+ 人为断开响应
  → postcondition 查不到 → outcome 改写为 confirmed_failure
  → 允许安全降级重试
  → 最终 submissions 数量 == 1
```

**DoD 追加**：三个子场景的 `submissions` 最终数量必须**全部为 1**。任何一个出现 2，视为实现失败。

## P0-2 · sanitize 结构化处理约束

### 问题

v1.1 的 T-02 描述 sanitize"支持递归对象、header map、form 字符串与普通文本的 **best-effort** 脱敏"，同时 T-30 又要靠 fingerprint 等值匹配做依赖识别。

裂缝在于：如果对整个 `postData` 字符串（如 `type=workday&approvalToken=abc123`）做整串处理，得到的 fingerprint 是对整串算的，与 response JSON 中那个独立字段值的 fingerprint 对不上，**依赖识别直接失效**——而依赖识别正是 M5 的出口标准。

依赖识别不能建立在 best-effort 之上。

### 变更 2.1 — T-02 sanitize 规格收紧

替换 v1.1 T-02 中 `sanitize.ts` 的描述为：

```
packages/core/src/sanitize.ts —— 全链路统一脱敏器

【处理顺序：必须先结构化解析，再逐字段处理】

1. Header map → 逐 key 判断，命中
   authorization|cookie|set-cookie|x-api-key|proxy-authorization|x-csrf-token
   → 值替换为 fingerprint(value)

2. postData / responseBody → 先按 content-type 解析：
   - application/json        → JSON.parse，递归遍历叶子
   - x-www-form-urlencoded   → URLSearchParams 解析成 kv，逐值处理
   - multipart/form-data     → 解析 part，逐 part 处理
   - text/html               → 只对 input[type=hidden] 的 value 做处理（ViewState）
   - 解析失败                 → 才退化到整串正则 best-effort，
                               并在结果中标记 { sanitizeMode: 'fallback' }

3. 逐字段判断：key 命中
   password|passwd|access_token|refresh_token|token|session|secret|api_key
   |__VIEWSTATE|__EVENTVALIDATION|__RequestVerificationToken
   → 值替换为 fingerprint(value)

4. fingerprint(value) 定义：
   `<REDACTED:sha256:${sha256(salt + value).slice(0,12)}>`
   - salt 为单次录制会话内的随机值，存于内存，不落盘
   - 同一会话内：同一原值 → 同一 fingerprint（保证依赖识别可用）
   - 跨会话：同一原值 → 不同 fingerprint（防止跨录制关联反推）
   - 不可逆：无法从 fingerprint 恢复原值
```

### 变更 2.2 — T-02 验收用例追加

v1.1 已有"同 token 同 fingerprint / 异 token 异 fingerprint"，追加两条**跨编码格式**的用例：

```ts
it('跨编码格式的同一 token 必须产生相同 fingerprint', () => {
  const token = 'tk_9f3a2c8e1b';
  const s = createSanitizer();                      // 同一会话

  // response 侧：JSON 字段
  const resp = s.sanitizeBody(
    JSON.stringify({ approverId: 1023, approvalToken: token }),
    'application/json'
  );

  // request 侧：form 编码字段
  const req = s.sanitizeBody(
    `type=workday&approverId=1023&approvalToken=${token}`,
    'application/x-www-form-urlencoded'
  );

  const fpFromResp = JSON.parse(resp).approvalToken;
  const fpFromReq  = new URLSearchParams(req).get('approvalToken');

  expect(fpFromResp).toMatch(/^<REDACTED:sha256:[0-9a-f]{12}>$/);
  expect(fpFromReq).toBe(fpFromResp);               // ← 关键断言
});

it('URL query 中的 token 也必须被处理且 fingerprint 一致', () => {
  const token = 'tk_9f3a2c8e1b';
  const s = createSanitizer();
  const url = s.sanitizeUrl(`/api/x?approvalToken=${token}&type=workday`);
  expect(url).toContain('<REDACTED:sha256:');
  expect(url).toContain('type=workday');            // 非敏感参数保留
});
```

### 变更 2.3 — T-24 追加约束

在 v1.1 的 T-24 交付要点中追加：

- **必须把 content-type 传给 sanitizer**，不得让 sanitizer 猜
- **URL 也要过 sanitizer**（`sanitizeUrl`），token 可能在 query string 里
- `RecordedRequest` 新增一个诊断字段：

```ts
export interface RecordedRequest {
  // ... v1.1 原有字段不变
  /** 【v1.2 新增】脱敏方式：structured = 结构化逐字段；fallback = 整串正则 */
  sanitizeMode: 'structured' | 'fallback' | 'none';
}
```

**追加验收**：加班流程录制后，`approver` 与 `submit` 两条请求的 `sanitizeMode` 必须都是 `structured`。若出现 `fallback`，说明解析逻辑没覆盖到，需修复而非放行。

### 变更 2.4 — T-30 追加验收

在 v1.1 的 T-30 验收中追加一条前置断言：

```
0. 前置检查：参与依赖识别的两条请求，sanitizeMode 必须均为 'structured'。
   若为 'fallback'，直接判定该任务不通过——依赖识别不允许建立在
   best-effort 脱敏之上。
```

### 备选方案（若 2.1–2.4 实施后仍不稳）

若在 M4/M5 阶段发现 fingerprint 关联仍不可靠，启用**方案 B**作为后备：

> **依赖识别前移到录制进程内完成。** 在 `record()` 结束、写盘之前，用**未脱敏的原始值**跑一遍 T-30 的依赖识别，把结果作为 `RecordSession.dependencies` 写入 record.json；随后再对 headers/body/url 脱敏落盘。analyzer 直接读 `dependencies`，完全不依赖 fingerprint。

代价：T-24 / T-29 / T-30 的边界要重划（依赖识别从 analyzer 移到 recorder）。
**决策点**：M4 结束时评估。若 T-24 验收中出现任何 `fallback`，即启用方案 B。

## P1-1 · `not_sent` / `outcome_unknown` 判定改为机械规则

### 问题

v1.1 的 T-37 措辞"`fetch` 在请求可能已经发出后超时/连接断开/response 丢失 → `outcome_unknown`"，会诱导 Codex 去区分"请求发出了没有"。

但浏览器 `fetch()` 抛 `TypeError: Failed to fetch` 时，无法区分是 DNS 失败、连接被拒、还是已发出但响应丢失。任何试图区分的实现都是猜测，且猜错方向就是重复提交。

### 变更 3.1 — T-37 判定规则替换

用以下**机械规则**替换 v1.1 T-37 中的 outcome 判定描述：

```
ExecutionOutcome 判定（按代码执行位置划分，不做异常类型推测）：

┌─ 阶段 1：fetch 调用之前 ─────────────────────────┐
│  模板变量解析失败                                  │
│  参数 Schema 校验失败                              │
│  preflight 未取到必需变量                          │
│  onConfirm 返回 false                             │
│  → 一律 not_sent                                  │
└──────────────────────────────────────────────────┘
                    ↓ 进入 fetch()
┌─ 阶段 2：fetch 已调用 ───────────────────────────┐
│  ⚠️ 从这一行开始，任何异常一律 outcome_unknown      │
│                                                   │
│  收到响应：                                        │
│    2xx + 断言通过        → confirmed_success       │
│    4xx/5xx 且响应体明确  → confirmed_failure       │
│      表明未产生副作用      （如 400 参数校验失败）    │
│    4xx/5xx 但无法判断     → outcome_unknown         │
│      是否已产生副作用                                │
│                                                   │
│  未收到响应（catch）：                              │
│    任何异常类型          → outcome_unknown          │
│    （不区分 TypeError / AbortError / 超时）          │
└──────────────────────────────────────────────────┘
```

实现上用一个显式标志位，不靠异常类型判断：

```ts
const result = await page.evaluate(async (req) => {
  let fetchStarted = false;
  try {
    fetchStarted = true;              // ← 就在 fetch 前一行置位
    const res = await fetch(req.url, { /* ... */ });
    return { fetchStarted, status: res.status, text: await res.text() };
  } catch (e) {
    return { fetchStarted, error: String(e), status: null, text: null };
  }
}, resolved);

// Node 侧判定
if (!result.fetchStarted) return outcome('not_sent');
if (result.status === null) return outcome('outcome_unknown');   // 无条件
// ... 后续按 status 与断言判定
```

**注意**：`fetchStarted` 必须在 `fetch()` **调用前**置位，不能在之后。这样它的语义是"我已经进入了可能产生副作用的区域"，而不是"请求确实发出去了"——后者客户端根本无从得知。

### 变更 3.2 — §6 坑位表条目替换

把 v1.1 §6 中这一行：

| 把所有 network catch 当失败 | 服务端可能已 commit，随后 UI 又提交一次 | 区分 `ExecutionOutcome`；连接断开/超时可能是 `outcome_unknown` |

替换为：

| 试图从异常类型区分「请求发没发出去」 | `TypeError: Failed to fetch` 涵盖 DNS 失败、连接拒绝、响应丢失，无法区分；猜错即重复提交 | 用 `fetchStarted` 标志位：置位在 `fetch()` 调用**前一行**；置位后的任何异常一律 `outcome_unknown`，不做类型推测 |

## P1-2 · 周期调整：7 周 → 8 周

v1.1 相对 v1.0 增加了四态 outcome、四态 auth、全链路 sanitizer、resolve/action 分离；v1.2 再加 postcondition 全链路。M6 与 M7 工作量实质增加，周数不动不现实。

### 变更 4.1 — §0.4 里程碑总览替换

| 里程碑 | 周 | 任务 | 出口标准 |
|---|---|---|---|
| **M0 骨架** | W1 前半 | T-01 ~ T-03 | `build`/`test`/`tsc` 全绿；§2 契约（含 **postcondition**）人工确认后冻结 |
| **M1 Mock 环境** | W1 | T-04 ~ T-10 | 朴素选择器必须失败；依赖陷阱能阻止跳过 approver；**history 能查到真实提交** |

| **M5 分析器** | W5 | T-29 ~ T-34 | 依赖识别含 approvalToken；**draft 含 postcondition 草稿或明确 TODO** |

新增子命令 `dsh doctor --probe-frontend <url>`，在目标页面注入探测脚本：

```js
(() => {
  const r = { vue: null, ui: null, evidence: [] };

  // Vue 版本探测
  if (window.__VUE__) { r.vue = 3; r.evidence.push('window.__VUE__'); }
  else if (window.Vue?.version) {
    r.vue = parseInt(window.Vue.version); r.evidence.push('Vue.version=' + window.Vue.version);
  } else if (document.querySelector('[data-v-app]')) {
    r.vue = 3; r.evidence.push('[data-v-app]');
  }

  // Element 版本探测：Plus 与 UI 的差异类名
  const hasPlus = document.querySelector('.el-config-provider, .el-overlay');
  const hasUI   = document.querySelector('.el-dialog__wrapper, .v-modal');
  if (hasPlus) { r.ui = 'element-plus'; r.evidence.push('.el-overlay / .el-config-provider'); }
  else if (hasUI) { r.ui = 'element-ui'; r.evidence.push('.el-dialog__wrapper / .v-modal'); }

  return r;
})();
```

输出示例：
```
前端框架探测结果（http://oa.corp.local/overtime/apply）
  Vue 版本      : 2   （依据: Vue.version=2.6.14）
  组件库        : element-ui   （依据: .el-dialog__wrapper, .v-modal）
  → 结论：需启用 T-09-vue2 / T-13 / A8
```

**这条探测应该在内网现场第一天就跑**，结果直接决定这三个任务做不做。
