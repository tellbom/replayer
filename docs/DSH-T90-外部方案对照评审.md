## 1. 背景：需要确认的核心问题

### 1.1 触发本次评审的疑问

当前设计中，一个业务变体对应一个独立 skill。例如请假流程：

```
skills/leave_compensatory.yaml    调休（无出差地点字段）
skills/leave_business_trip.yaml   公假出差（多一个出差地点字段）
skills/leave_sick.yaml            病假
```

**疑问**：录制调休时页面上不存在"出差地点"字段，探针无法记录一个不存在的元素。若用户实际要提交公假出差，必须重新录制一次。

这带来两个问题需要确认：

- **Q1**：这种"一变体一 skill"的策略，在业界是主流做法还是权宜之计？
- **Q2**：是否存在"录制一次、自动泛化到所有变体"的成熟方案？

### 1.2 需要评审者自行验证的初步判断

以下是待验证的初步判断，**不是结论**。评审时请独立核实，不同意就推翻：

| 初步判断 | 需验证 |
|---|---|
| 多录制是工程界主流做法 | 查证同类开源项目的实际做法 |
| "一次录制自动泛化"目前只在研究阶段，无可直接用的开源实现 | 查证是否有生产可用的实现 |
| DSH 在安全语义上（四态 outcome、语义漂移、写确认）走得比同类项目远 | 逐项对照确认 |

## 2. 对照对象

### 2.1 一级对照：browser-use/workflow-use【必做】

仓库：`https://github.com/browser-use/workflow-use`

**这是与 DSH 定位最接近的开源项目**，自述为「RPA 2.0」，核心机制：

- 把流程演示给录制器看，自动生成工作流
- 生成带变量的确定性工作流
- `workflow.run_with_no_ai()` —— 零 LLM 执行
- 步骤失败时回退到 browser-use agent
- roadmap 含「自愈：失败时 agent 自动接管并更新工作流文件」

**注意**：该项目自述处于非常早期开发阶段，不建议生产使用。**评审时不要因为"它是官方项目"就默认它的设计更优**。

#### 必须完成的对照

**A. Schema 逐字段对照**

拉取其 `workflow.json` 的结构定义（或从示例文件反推），与 DSH 的 `SkillSchema` 做逐字段对照表：

| workflow-use 字段 | DSH 对应字段 | 差异 | 判断 |
|---|---|---|---|
| ... | ... | ... | 借鉴 / 我们更优 / 无关 |

重点关注：
- 变量/参数是怎么定义和绑定的（**对照 T-86 的参数化修复**）
- 步骤怎么表达（是否有 channel 概念，还是全 UI）
- 定位信息怎么存（selector 形态、有无 confidence 概念）
- 有没有条件分支 / 循环
- 有没有等待条件、前置条件的表达
- 失败处理怎么写在 schema 里

**B. 变量提取机制对照**

它自述「自动从表单提取变量」。查明：
- 用什么规则识别哪些值是变量
- 有没有 enum 类型的处理
- **是否存在 DSH T-86 遇到的"从响应数组取固定下标"这类问题**
- 有没有"参数声明了但没被引用"的检查

**C. 失败与回退对照**

- 它的 LLM 回退在什么条件下触发
- 有没有区分"请求未发出"和"结果未知"（对照 DSH 的 `ExecutionOutcome` 四态 / C12）
- **重点**：写操作失败时它怎么处理？有没有防重复提交的机制？
- 有没有人工确认环节

**D. 会话/认证对照**

- 它怎么处理登录态
- 是否支持复用已登录浏览器
- 有没有会话过期处理

**E. 多变体处理对照**

- 它是一个变体一个 workflow，还是支持条件分支？
- 若支持分支，分支条件怎么表达、怎么录制？

### 2.2 二级对照：研究方向【只读文献，不实现】

以下三个方向**只需阅读并总结**，明确标注「不在本轮实现范围」。

#### AutoRPA（arXiv 2605.21082, ICML 2026）

核心机制：ReAct agent 探索收集成功轨迹 → 「翻译 agent」把硬编码的 ReAct 步骤转换为**软编码动作**，使其能在变化环境中动态执行。

**评审要点**：
- "软编码动作"具体是什么形态？能否用一个例子说明？
- 它是否解决了 §1.1 的 Q1 问题（一次录制覆盖多变体）？
- 它依赖 agent 自主探索——这与 DSH 明确排除 J4 开放式探索是否冲突？
- 有无开源实现？若有，成熟度如何？

#### Agent Workflow Memory（arXiv 2409.07429, ICML 2025）

仓库：`https://github.com/zorazrw/agent-workflow-memory`

核心机制：从轨迹中归纳工作流，「把示例特定的上下文抽象掉」。

**评审要点**：
- 它是从**单条**轨迹泛化，还是从**多条**轨迹归纳共性？
- 若是后者，那么 DSH 的"多录制"其实是它的**输入前提**而非对立面——请确认这个理解
- 归纳出的 workflow 是自然语言还是结构化的？能否直接执行？
- 对 DSH 有无可借鉴的具体技术（而非仅思路）？

#### 企业 BPM 分级自动化（arXiv 2604.23855）

核心机制：从操作员行为学工作流，分阶段推进——离线轨迹训练 → copilot 监督 → 门控后台执行（只有高置信度动作才自动化）。

**评审要点**：
- 它的分阶段结构与 DSH 的 `draft → verified → 自动运行` 是否同构？
- **它的置信度门控怎么设计的？** 阈值怎么定？这是本条最有价值的部分
- 它有没有"错误自动回退到人工"的机制？
- 与 DSH T-79/T-84 的状态机对比，有无值得吸收的地方

### 2.3 三级对照：传统 RPA 的多变体实践【简要即可】

UiPath / Automation Anywhere / Blue Prism 等成熟 RPA 平台面对同一表单多变体时的标准做法。

**评审要点**（不需要深入，各一两句即可）：
- 是一变体一流程，还是带条件分支的单一流程？
- 若支持分支，是录制时录多次合并，还是手工在设计器里加分支？
- 业界对"分支复杂度 vs 流程数量"的权衡有无共识？

## 5. 评审要求

### 5.1 诚实优先

**这次评审的价值在于找到我们漏掉的东西，不在于证明我们是对的。**

- 若发现 DSH 某个设计确实不如外部方案，**明确说出来**，不要为现有设计辩护
- 若发现某个我们认为的"优势"其实是过度设计，**明确说出来**
- 若某个问题查不到答案，写"未能确认"及尝试过的方法，**不要推测后当作结论**

### 5.2 证据要求

| 结论类型 | 证据要求 |
|---|---|
| 关于 workflow-use 的行为 | **必须引用代码或文档原文**，注明文件路径/URL |
| 关于研究论文的机制 | 引用论文章节或摘要原文 |
| 关于传统 RPA 的做法 | 引用官方文档；查不到就写"未能确认" |
| 主观判断 | 明确标注为"评审者判断"，与事实分开 |

### 5.3 不要做的事

- ❌ 不修改 `packages/` 下任何代码
- ❌ 不引入任何新依赖
- ❌ 不因为外部项目有某功能就直接实现
- ❌ 不修改 T-79~T-89 的任何既有文档

### 5.4 时间盒

本任务是评审，**不应超过 T-86~T-89 开发工作量的 20%**。若某个对照项查证成本过高（如需要深入阅读大量源码），标注"部分完成"并说明剩余部分，不要无限深入。

## 6. 注意事项

### 6.1 不要被"官方项目"光环影响判断

workflow-use 出自 browser-use 团队，但它**自述处于非常早期开发阶段、不建议生产使用**。

DSH 在若干方面（写操作安全语义、会话持有、语义漂移防护）可能已经走得更远。**评审要基于实际代码和文档，不基于项目知名度。**

### 6.2 区分"没做"和"不需要做"

若发现 workflow-use 缺少 DSH 有的某个机制，先判断：

- 是它还没做到（DSH 领先）
- 还是它的场景不需要（DSH 可能是过度设计）

例如：workflow-use 主要面向公网网站自动化，DSH 面向企业内网提交业务单据。**后者对"重复提交一张请假单"的容忍度远低于前者对"重复点一次搜索"**。这个差异会解释很多设计分歧。

**请在报告中明确区分这两种情况。**

### 6.3 多录制问题的答案可能是"没有更好的答案"

§1.1 的 Q1 可能没有令人满意的解法。如果查证结果是「业界普遍都在多录制，泛化方案还在实验室」，**这本身就是一个有价值的结论**，可以让我们安心继续当前策略。

**不要为了让报告"有产出"而推荐一个不成熟的方案。**

### 6.4 v2.0 约束与 T-79 裁决继续有效

评审可以质疑这些约束，但**质疑要写在报告里，不要在代码中实践**。特别是：

- C2（页面内 fetch）、C6（写确认）、C8（凭证不落盘）、C12（四态）、C16（不代替登录）
- T-79 §12 禁止扩范围清单
- T-84 的语义漂移防护

若外部方案在某处与这些约束冲突，**如实记录冲突**，由人工裁决是否调整约束。
