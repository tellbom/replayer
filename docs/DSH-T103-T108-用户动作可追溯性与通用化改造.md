## 0. 裁决

### 0.1 关于「严格照用户动作回放」的提议

项目方提出：是否可以只跟随用户点击及其触发的请求，全部记录后原样回放，以此规避 F-1。

**裁决：原则采纳，字面实现不采纳。**

| 部分 | 裁决 | 理由 |
|---|---|---|
| **原则**：回放的请求必须源自用户实际做过的动作 | ✅ **升格为硬约束（C25）** | F-1 的根因正是分析器生成了用户从未执行过的独立请求 |
| **实现**：原样重放录制到的全部请求 | ❌ 不采纳 | 三个不可回避的问题，见下 |

**不采纳字面实现的三个理由**：

1. **录制到的值是死的**。一次性值（页面实例绑定的隐藏字段值、单活令牌）原样重放必然失败；用户输入的值必须可参数化替换。区分这两类需要溯源分析，无法省略。
2. **噪音请求会被一起重放**。一次用户动作可能触发十余个请求（静态资源、埋点、轮询、权限查询）。全部重放会污染统计数据、显著拖慢执行、并产生大量无意义的失败判断。
3. **纯前端交互不产生请求**。日期面板选择、复选框勾选、下拉选值等步骤没有对应的网络请求，若只按请求回放，提交时表单为空。

**结论**：「跟随用户动作」是正确的**约束**，但录制到的是一次具体执行，回放需要的是可重复的模板。中间的翻译层（哪些重取、哪些参数化、哪些丢弃）不可省略。

本轮的做法是：**把「跟随用户动作」写成硬约束，用它来纠正分析器当前的越界行为**，而不是取消分析层。

## 1. 新增架构约束

追加到 v2.0 §1 约束表。

| # | 约束 | 原因 |
|---|---|---|
| **C24** | **通用化约束**：任何测试环境（Mock、fixture、真实系统）中发现的问题，只有在能表述为浏览器 / DOM / HTTP / 数据流层面的通用规则后，才允许进入 `packages/*`。**端点名、业务字段名、框架名、认证产品名、Mock 路径、固定数量指标不得进入通用判断逻辑。** 阈值必须为具名常量或配置项 | 测试环境是回归夹具，不是产品模型。按具体环境写死判断逻辑，会让产品只在该环境成立 |
| **C25** | **用户动作可追溯性**：回放中的每一个请求步骤，必须可追溯到录制中的一个用户动作。**分析器不得生成用户未执行过的独立请求步骤。** 需要重新获取的值，必须从用户实际动作所产生的页面或响应中提取 | F-1 的根因。分析器自行推断出的独立请求，其时机不受用户动作序列约束，会与真实执行顺序冲突 |
| **C26** | **页面实例作用域**：从页面 DOM 提取的值，其有效性绑定于**该次页面加载**。提取时机必须满足「在最后一次导航到该页面之后」且「在使用它的请求之前」 | HTML 语义：隐藏字段的值随页面渲染产生，不同次加载可能不同。这是通用事实，与字段名、框架、后端技术无关 |
| **C27** | **分析器输入容错**：录制数据是不可信输入。分析器对任何录制输入都不得抛出未捕获异常；无法处理的最坏结果是 `TODO_UNRESOLVED` 并在 `_notes` 说明，draft 仍须产出 | F-2。真实页面必然包含空值、运行时生成的标识、异常结构。分析器的容错等级应等同于 parser |
| **C28** | **参数身份来自控件身份**：参数与控件实例一一对应。**不得因值相同或相似而合并参数。** 同一参数不得被多个不同控件实例引用，除非显式声明共享 | F-4。按值去重会导致两个字段共用一个参数，回放时把同一个值填进不同字段——静默数据错误 |

### 1.1 C24 的豁免清单

以下不属于「通用判断逻辑」，不受 C24 约束：

| 项 | 性质 | 说明 |
|---|---|---|
| `el-locator` 中的组件库类名 | **执行层兼容代码** | 它是 UI 动作的执行适配（如浮层挂载位置、动画等待），不参与定位生成或质量判定。T-83 已确认保留 |
| `entry` / `skill` 配置中的选择器、端点、字段名 | **配置数据** | 由录制产生或人工填写，随系统而变，本就该是具体值 |
| 测试代码中的具体值与数量断言 | **测试** | 验收标准可以有具体数字 |
| `sanitize` 的敏感字段默认清单 | **安全兜底**（需改造） | 见 §7.2：应从代码移到可扩展配置，产品内置默认值 |

## 2. T-103 · 用户动作可追溯性与页面实例作用域提取

### 2.1 问题

回放时出现一次用户从未执行过的请求：

```
① preflight：独立发起一次请求以提取页面中的隐藏字段值
   → 服务端返回值 V1，并将 V1 记为当前有效
② 步骤 s2：导航到同一页面
   → 服务端返回值 V2，V1 作废
③ 步骤 s7：提交，携带 ① 提取的 V1
   → 服务端拒绝（400）
```

用户手动操作时只加载过一次页面，只有一个有效值。**多出来的 ① 是分析器推断生成的，用户从未执行。**

**通用形态**：任何「每次页面加载即轮换、仅最新值有效」的隐藏字段，在「独立 preflight + 后续导航」组合下都会失败。这类形态在服务端渲染的老系统中很常见，不限于任何特定后端技术。

### 2.2 根因（两处）

**a) 分析器的生成策略越界**

当前实现按**字段名匹配**来识别需要 preflight 的值（硬编码了若干已知字段名的正则），并固定生成「独立 GET + DOM 提取」的形态。

两个问题：
- 违反 C24（字段名进入通用判断逻辑）
- 违反 C25（生成了用户未执行的请求）

**b) preflight 的执行时机不可控**

`preflight` 是全局前置，跑在所有步骤之前。即使改用页面态提取（`PreflightSchema.request` 省略时即为「从当前页面 DOM 提取」，该模式**已在契约中存在**），执行时页面也尚未导航到目标位置。

### 2.3 交付

#### ① 值来源识别改为因果匹配（替代字段名匹配）

分析器对 mutating 请求体中每个无法溯源的字面量，按序判定：

```
① 是否等于某个用户动作的输入/选择值            → 参数
② 是否出现在某个前置响应体中（过弱值过滤）      → 跨步依赖
③ 是否等于某个 preflight 变量的当前值            → 变量引用
④ 是否等于录制期间某次页面加载中，
   某个「非用户可编辑元素」的值                  → 页面实例作用域值【新增】
⑤ 是否在豁免清单中                              → 常量
⑥ 以上皆否                                      → TODO_UNRESOLVED
```

**第 ④ 条的判定完全基于值匹配与元素性质，不涉及任何字段名。**

「非用户可编辑元素」的通用判据：
- `input[type=hidden]`
- 设置了 `readonly` 或 `disabled` 且录制中无用户交互记录的表单控件
- `<meta>` 的 `content`
- 录制中从未出现在任何用户动作 target 中的元素

**要求**：录制器需在每次页面加载/导航完成时，采集当前页面所有「非用户可编辑元素」的 `(定位描述, 值)` 快照，供分析器做第 ④ 条匹配。快照经 `sanitize` 后落盘。

#### ② 提取步骤的生成与放置

命中第 ④ 条时：

```
定位「该值所属的那次页面加载」对应的用户动作步骤 sN
  （即最后一次导航到该页面的步骤）

在 sN 上生成提取声明：
  sN.extract = { <varName>: <该元素的定位描述> }

后续使用该值的请求，引用 {{varName}}

【禁止】生成独立的 preflight 请求步骤
```

若找不到对应的导航步骤（即该值来自录制中未捕获的页面加载）：
```
→ TODO_UNRESOLVED
→ _notes：「该值来源于某次页面加载中的非用户可编辑元素，
            但录制中未找到对应的导航步骤。
            请确认录制是否完整，或手动指定提取位置。」
```

#### ③ 步骤级提取的执行

`UiActionSchema` 已有 `extract` 字段（`z.record(z.string()).optional()`），需确认/实现其执行：

```
navigate 或任何 ui 动作完成后：
  1. await settleNavigation（若发生导航）
  2. 在页面上下文内执行 extract 声明
  3. 结果写入 ctx.vars
  4. 后续步骤可引用
```

**提取必须在页面上下文内执行**（C2），且在导航稳定之后（C22 相关）。

#### ④ preflight 的适用范围收窄

`preflight` 保留，但其带 `request` 的形态**仅当该请求在录制中真实存在、且可追溯到某个用户动作时**才允许生成（C25）。

```
分析器生成 preflight-with-request 的前置条件：
  该请求在 RecordSession.network 中存在
  且 该请求已归属到某个用户动作
否则：
  → 改用步骤级 extract（②）
  → 或 TODO_UNRESOLVED
```

**说明**：页面加载本身也是用户动作的结果（导航），因此由导航触发的初始化请求是可追溯的，合法。不合法的是分析器凭字段名推断出来、录制中并不存在的请求。

#### ⑤ 契约变更（允许）

```ts
// RecordSession 新增
export interface PageSnapshot {
  ts: number;
  url: string;
  /** 对应的用户动作序号（导航动作） */
  actionIdx: number | null;
  /** 非用户可编辑元素的值快照 */
  immutableValues: Array<{
    locator: LocatorStrategy;
    value: string;          // 已过 sanitize
    kind: 'hidden' | 'readonly' | 'disabled' | 'meta' | 'untouched';
  }>;
}

export interface RecordSession {
  // ... 现有字段
  pageSnapshots: PageSnapshot[];    // 【新增】
}
```

`UiActionSchema.extract` 已存在，无需新增；若未实现执行逻辑，本任务补齐。

## 3. T-104 · 分析器输入容错

### 3.1 问题

分析器在遇到以下录制输入时**抛出未捕获异常，draft 生成中断**：

- 动作的可见文本为空（如无文字的图标类控件）→ Schema 校验抛错
- 控件标识符为运行时生成、跨渲染不稳定 → 被参数化后无引用，抛「未引用参数」错误

同族问题：**分析器把录制数据当成可信输入**。真实页面必然包含空值、运行时生成的标识、异常结构。

### 3.2 交付

#### ① 通用容错约束（C27）落地

```
分析器的所有入口函数（draft 生成、参数标注、依赖识别、preflight 检测）：
  - 对单个动作/请求的处理失败，不得中断整体流程
  - 失败项降级为 TODO_UNRESOLVED，记录原因到 _notes
  - draft 必须产出（哪怕全是 TODO）
  - 仅当输入根本不是合法 RecordSession 时才允许抛错
```

实现要求：每个动作/字段的处理包在独立的错误边界内，失败只影响该项。

#### ② 空值处理

```
动作的可见文本 / 标签 / 值为空或缺失：
  - 不参与参数化
  - 不进入 params 声明
  - 该步骤保留（仍可执行）
  - _notes 记录：「步骤 sN 无可识别文本，无法参数化，
                  若该步骤涉及可变输入请手动补充」
```

#### ③ 不稳定标识符检测（通用判据）

**不使用框架前缀匹配。** 两个通用信号：

```
信号 A · 跨录制不稳定
  存在两份同流程录制时，对比同一位置控件的该属性值
  值不同 → 判定为不稳定标识符

信号 B · 高熵启发（单录制时）
  属性值中包含连续的高熵字符段
  （字符集为 base36/hex，长度超过阈值，且不构成可读词）
  → 疑似运行时生成

阈值走 constants.ts 具名常量，不得硬编码在判断分支中
```

判定为不稳定标识符的属性：
- 不参与参数化
- 不作为定位依据（若已作为定位依据，降级 confidence）
- `_notes` 记录

#### ④ 契约变更

```ts
// constants.ts 新增
export const IDENTIFIER_STABILITY = {
  /** 高熵段最小长度，超过则疑似运行时生成 */
  minEntropySegmentLength: 6,
  /** 判定为高熵所需的最小字符集多样性 */
  minCharsetDiversity: 2,
} as const;
```

## 4. T-105 · 参数身份规则与定级

### 4.1 第一步：定级【最先执行】

现象：两个不同的文本输入控件被绑定到同一个参数。回放时传入一个值，两个控件都会被填入该值。

**必须先回答一个问题**：这种情况下能否走到提交？

```
构造场景：
  录制两个不同文本控件的输入
  观察 draft 中两者是否被绑定到同一参数
  若是 → 回放并观察：
    a. 是否在提交前被某个护栏拦截（TODO_UNRESOLVED / 溯源失败 / 校验）
    b. 是否能走到提交且服务端接受
```

| 结果 | 定级 |
|---|---|
| 存在「绑错且能提交」的路径 | **P0 静默错误**，本轮最高优先级 |
| 所有路径都被护栏拦截 | P2，仍需修复但不阻塞 |

**定级结论必须先报告，再进行修复。**

### 4.2 修复：参数身份规则（C28）

```
参数与控件实例一一对应。

去重依据：控件身份，不是值。
  控件身份 = 稳定定位描述 + 在其容器内的位置
  （不含运行时生成的标识，见 T-104 ③）

禁止：
  - 因两个动作的值相同/相似而合并参数
  - 因参数命名冲突而复用已有参数

命名冲突时：
  自动加区分后缀，而非合并
```

### 4.3 附带修复

`expectsRedirect` 被错误地附加到不产生导航的动作上（如文本填写），导致回放时等待导航必然超时。

```
expectsRedirect 仅允许出现在满足以下条件的步骤：
  该步骤在录制中，其后紧跟一次导航
  且该步骤是 mutating 请求或 form 提交类交互
```

### 4.4 验收

| # | 项 | 期望 |
|---|---|---|
| V-105-0 | **定级结论** | 明确回答「绑错能否走到提交」，附复现证据 |
| V-105-1 | 控件身份去重 | 两个不同控件即使录制值相同，也产生两个独立参数 |
| V-105-2 | 命名冲突 | 参数名冲突时加后缀区分，不合并 |
| V-105-3 | 回放正确性 | 传入两个不同值 → 两个控件分别填入各自的值 |
| V-105-4 | 服务端核验 | 提交后查询服务端记录，两个字段的值各自正确 |
| V-105-5 | expectsRedirect | 非导航型步骤不再带 `expectsRedirect`，回放不超时 |
| V-105-6 | 显式共享 | 若确需多控件共用一个参数，支持显式声明（不自动推断） |

## 5. T-106 · 身份变更阻断端到端验证

### 5.1 背景

身份一致性校验（C21）已连续三轮处于「代码存在、单测通过、端到端未验证」状态：

| 轮次 | 状态 |
|---|---|
| 第一轮 | 侧路配置下身份指纹恒定，机制实际惰性 |
| 第二轮 | 未覆盖 |
| 第三轮 | **PASS（佐证）/ NOT VERIFIED（端到端）**，理由：fixture 单用户 |

项目历史上已有同类教训（核心验收测试崩溃后跨越多个任务无人发现）。**本轮不接受代码佐证。**

### 5.2 交付

**① fixture 支持多账号**

回归夹具需支持至少两个可区分身份的账号，身份探测端点返回值随账号变化。

**② 端到端验证场景**

```
场景 A · 回放中途换身份
  1. 账号一登录，开始回放多步技能，记录初始身份指纹
  2. 中途使会话失效
  3. 用账号二完成登录
  4. 期望：检测到身份不一致 → 立即中止 → 不执行任何后续步骤
     服务端记录增量为 0

场景 B · 录制中途换身份
  1. 账号一登录，录制若干步
  2. 中途使会话失效
  3. 用账号二完成登录
  4. 期望：中止录制，标记身份已变更，已录部分保留，不续录

场景 C · 同身份恢复（对照组）
  1. 同上，但仍用账号一登录
  2. 期望：正常恢复，从锚点重跑（C22）
```

### 5.3 验收

| # | 项 | 期望 |
|---|---|---|
| V-106-1 | fixture 多账号 | 两个账号的身份探测返回值不同 |
| V-106-2 | 回放换身份中止 | 场景 A：中止，服务端增量 0 |
| V-106-3 | 录制换身份中止 | 场景 B：中止，已录部分保留，标记身份变更 |
| V-106-4 | 同身份恢复 | 场景 C：正常从锚点重跑 |
| V-106-5 | 指纹差异 | 两账号的身份摘要值不同（贴实际值） |
| V-106-6 | 报错可读 | 中止时的报错信息说明「身份已变更」，不是泛化的执行失败 |

## 6. T-107 · 跳转式认证系统冷启动防护

### 6.1 背景

实测观察：某类系统在浏览器冷启动时会经历多跳认证重定向闭环，耗时数秒。若在闭环完成前发起导航，会被打断导致卡死。使用常驻会话（附着模式）时无此问题。

**通用判据（不涉及任何认证产品名）**：

```
entry 满足以下两条时，判定为跳转式认证系统：
  ① sessionType 非 cookie（即 bearer / mixed）
  ② loginUrlPatterns 非空（存在认证跳转目标）
```

### 6.2 交付

**① 冷启动警告**

```
dsh record / dsh replay 启动时：
  若 entry 判定为跳转式认证系统
  且 无可用常驻会话
  → 输出警告：
    「该系统采用跳转式认证，冷启动可能因认证重定向竞态导致失败。
      建议先建立常驻会话后再执行。
      如需强制冷启动，请使用 --allow-cold-start。」
  → 默认拒绝执行（可用显式开关绕过）
```

**② 冷启动路径加固**（即使被绕过也应尽量可用）

```
冷启动且判定为跳转式认证系统时：
  1. 首次导航后强制 settleNavigation
  2. 认证跳转期间的导航不计入超时
  3. 达到稳定态后再执行 entry 的 landing 判定
```

**③ 文档**

在使用文档中说明：跳转式认证系统应优先使用常驻会话入口。

### 6.3 验收

| # | 项 | 期望 |
|---|---|---|
| V-107-1 | 判定正确 | 跳转式认证 entry 被识别；cookie 型 entry 不被误判 |
| V-107-2 | 默认拒绝 | 无常驻会话时冷启动被拒绝并给出建议 |
| V-107-3 | 显式绕过 | `--allow-cold-start` 可强制执行 |
| V-107-4 | 加固有效 | 强制冷启动时，认证跳转闭环不再导致卡死 |
| V-107-5 | 常驻路径不受影响 | 有常驻会话时无警告，行为不变 |
| V-107-6 | 无产品名 | grep 判定逻辑，不得出现任何认证产品名 |

## 7. T-108 · 枚举来源优先级与既有违规改造

### 7.1 枚举来源（F-5）

现象：枚举参数的映射表只包含录制时选中的那一个值，跨参数回放需人工补全。

**通用规则（不涉及端点名）**：

```
枚举选项集合的来源，按优先级：

① 录制时该控件在 DOM 中的全部可选项
   （原生 select 的 options、role=option 的元素集合等）

② 若该控件的选项由某个响应填充
   （因果关系由 DOM 变更观测提供：该响应到达后，
     该控件的可选项从空变为非空）
   → 从该响应构建【静态映射表】写入 draft

③ 都无法获取 → 只含录制值，_notes 标注「跨参数需人工补全」
```

**必须区分（在代码注释中写明）**：

| | 允许 | 禁止 |
|---|---|---|
| 形态 | 从响应构建静态映射表写入 draft | 运行时按数组下标取值 |
| 示例 | `enumMap: {A: a, B: b, C: c}` | `type: "{{sN[0].value}}"` |
| 差别 | 映射表是静态数据，回放时按参数查表 | 下标取值与调用方参数无关，永远取同一项 |

**先确认第 ② 级是否已实现**。若已实现但未生效，查明原因；若未实现，本任务补齐。

### 7.2 既有 C24 违规项改造

以下为当前代码中已存在的、违反 C24 的实现，本任务一并改造：

| # | 位置 | 违规 | 改造方向 |

| **R-1** | 分析器的 preflight 检测 | 按具体隐藏字段名的正则匹配识别需要预取的值 | **由 T-103 ① 的因果值匹配替代，删除字段名规则** |
| **R-2** | `sanitize` 的敏感字段清单 | 业务字段名硬编码在代码中 | 移到配置：产品内置默认清单，entry 层可追加。代码中只保留「读取配置并匹配」的逻辑 |

## 9. 注意事项

### 9.1 C24 是本轮的元约束

本轮所有改造都必须先通过一个检查：**这条规则换一个系统还成立吗？**

- 「隐藏字段的值绑定于该次页面加载」→ 成立，是 HTML 语义
- 「看到某某字段名就预取」→ 不成立，只在特定后端技术下成立

**当发现某条判断只在测试环境成立时，先找它背后的通用事实，找不到就不要进 `packages/`。**

### 9.2 C25 不等于取消分析层

「回放的请求必须可追溯到用户动作」约束的是**分析器不得凭空生成请求**，不是「原样重放录制内容」。

参数溯源、噪音过滤、UI 步骤保留三者不可省略，理由见 §0.1。

### 9.3 T-103 的价值不只是修 F-1

C25 一旦落地，将来分析器再想「自作主张加一步」都会被约束住。**这比修一个具体 bug 更重要。**

### 9.4 T-105 先定级再修复

定级结论会改变整轮优先级。**不要跳过定级直接修**——如果它是 P0，本轮的顺序和验收强度都要调整。

### 9.5 T-106 不接受代码佐证

这是第三次要求验证同一个机制。项目历史上已有「代码存在、测试崩溃、无人发现」的先例。**必须端到端复现。**

### 9.6 不要扩范围

发现值得做但不在本轮的，记录在报告「建议」段落，不要实现。T-91~T-96 §0.3 与 T-97~T-102 §0.3 的不做清单继续有效。

### 9.7 v2.0 约束继续有效

本轮特别相关：

| 约束 | 相关任务 |
|---|---|
| **C2** 页面内 fetch | T-103 步骤级 extract |
| **C11** 落盘前统一脱敏 | T-103 页面快照 |

## 10. 一句话总结

> 「跟着用户动作走」这个原则是对的，本轮把它升格为硬约束（C25）——
> 而 F-1 的根因，恰恰是分析器违反了这条原则，生成了一次用户从未执行过的请求。
> 修法不是取消分析层，是让分析层不再越界：需要重新获取的值，
> 从用户实际导航所产生的那次页面加载中提取，一次加载、一个值、取用同源。
