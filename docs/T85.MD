## 背景

v2.0 规格中，技能的每个步骤有 channel 属性（C1：**channel 是步骤级属性，不是技能级**），取值 `network / ui / merged / auto`。相关任务：

- **T-24** 网络录制（双时间戳 + 落盘前脱敏，`sanitizeMode` 须为 `structured`）
- **T-29** 动作-请求关联（**必须用 requestTs，不得用 responseTs**，C15）
- **T-30** 副作用与依赖识别（跨请求依赖，如 `approverId` / `approvalToken`）
- **T-33** draft 生成时判定 channel
- **T-37** network 通道执行器（**必须在 `page.evaluate` 内 fetch**，C2）

从 T-63 到 T-84 共二十余个任务全部围绕 Locator Engine。T-83 完成报告的验证清单为 `build / unit 152 / e2e 89 / T68-T74 + T84 25`，**未包含任何 network 通道相关项**。

在一个刚删除整个 legacy 引擎、修改过 recorder 注入契约（`__DSH_GEN__` → `__DSH_PWGEN__`）的代码库中，network 通道属于「长期未验证」状态。本次审计确认它是否仍然工作。

## 审计项

### A · 测试存活性

逐条执行，贴**原始输出**（含通过/失败/跳过数量）：

```bash
pnpm --filter e2e test -g "channel-network"
pnpm --filter e2e test -g "network-record"
pnpm --filter @dsh/analyzer test
pnpm --filter e2e test -g "fallback"
```

若某条 grep 匹配不到任何测试，明确写「无匹配测试」，不要静默跳过。

### B · 录制产物中的网络数据

用当前 Mock 环境完整录制一次加班申请流程（含选择加班类型触发联动），然后：

```bash
# 捕获到的请求总数
jq '.network | length' <record.json>

# 每条请求的关键字段
jq '.network[] | {method, url, mutating, sanitizeMode, requestTs, responseTs}' <record.json>

# sanitizeMode 分布（T-24 DoD 要求全部为 structured）
jq '[.network[].sanitizeMode] | group_by(.) | map({mode: .[0], count: length})' <record.json>
```

**必答**：
1. `approver` 与 `submit` 两条请求是否都被捕获？
2. 两条的 `sanitizeMode` 是否都是 `structured`？出现 `fallback` 即为问题
3. 是否存在 `requestTs` 缺失或等于 `responseTs` 的记录？

### C · 动作-请求关联与依赖识别

对 B 步的录制运行分析器，检查：

```bash
dsh analyze <record目录> --out /tmp/audit-draft.yaml
```

**必答**：
1. `approver` 请求是否被关联到「选择加班类型」这个动作？
2. draft 中 `submit` 步骤的 body 是否含跨步模板引用（形如 `{{s2.approverId}}`、`{{s2.approvalToken}}`），还是把录制时的具体值硬编码了？
3. 打开 `packages/analyzer/src/correlate.ts`，**贴出关联逻辑中实际使用的时间戳字段名**。确认是 `requestTs` 还是 `responseTs`（C15）

### D · channel 判定分布

```bash
# 本次 draft 的分布
grep -c "channel: network" /tmp/audit-draft.yaml
grep -c "channel: ui"      /tmp/audit-draft.yaml
grep -c "channel: merged"  /tmp/audit-draft.yaml
grep -c "channel: auto"    /tmp/audit-draft.yaml

# 仓库中已有技能的分布
grep -c "channel: network" skills/*.yaml
grep -c "channel: ui"      skills/*.yaml
grep -c "channel: merged"  skills/*.yaml
```

**⚠️ 重点**：若 `channel: network` 计数为 0 而 `ui` 覆盖全部步骤，说明分析器已退化为「一切皆 UI」。**这是本次审计要找的头号问题。**

若出现这种情况，进一步定位是哪一环：
- 录制没抓到请求（B 步的 network 数组为空）
- 抓到了但关联失败（C 步 approver 未归属到任何动作）
- 关联成功但 channel 判定逻辑没走 network 分支（读 `packages/analyzer/src/draft.ts`）

### E · T-30 依赖陷阱是否仍然成立

这是 M5 的出口标准，**不能只用「原参数原样回放成功」来证明**。

```
1. 用 type=工作日加班 录制并生成技能
2. 人工修正 YAML（若 C 步发现是硬编码，先记录该事实，本步仍照做）
3. 回放时把参数改为 type=周末加班
4. 观察结果
```

**判定**：
- 若回放**成功** → 说明确实重新调用了 approver 并注入了新的 approvalToken，依赖识别正确 ✅
- 若回放**被 Mock 拒绝**（`approvalToken` 无效 / `approverId` 不匹配）→ 说明动态值被硬编码，依赖识别失效 ❌

贴出实际的请求体与响应。

### F · C2 约束是否仍被遵守

```bash
# network 通道不得使用 Node 侧 http 客户端
grep -rnE "axios|node-fetch|got\(|http\.request|https\.request" packages/replayer/src/
```

同时打开 `packages/replayer/src/channel-network.ts`，**确认业务请求是在 `page.evaluate` 内通过 `fetch` 发出的**，并贴出该段代码。

### G · Outcome 四态判定是否完好

打开 `packages/replayer/src/channel-network.ts`，确认 T-37 的机械规则仍在：

- 是否存在 `fetchStarted` 标志位？
- 该标志位是否置位于 `fetch()` **调用前一行**？
- `fetchStarted === true` 且未收到响应时，是否**无条件**返回 `outcome_unknown`（不按异常类型区分）？

贴出相关代码段。

若 Mock 仍支持 `drop_response=1`，跑一次验证：

```
POST /api/overtime/submit?drop_response=1
→ 期望 outcome = outcome_unknown
→ 期望 /api/_debug/submissions 计数为 1（服务端已创建）
→ 期望不发生自动 UI fallback（C12）
```
