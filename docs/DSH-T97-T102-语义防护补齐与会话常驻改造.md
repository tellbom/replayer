## 1. 背景：本轮要解决的核心事实

### 1.1 P0 实证：语义漂移防护存在真空区

GLM 用注入实验证明了 T-84 的失效路径：

```
录制时：radio >> nth=1  →  「紧急」(urgency=URGENT)
注入漂移：前置插入一个新 radio
回放时：nth=1  →  「一般」(urgency=NORMAL)
结果：ok=true，4378ms，s3 步骤 ✓ 通过，无任何告警
```

**点错了控件，回放整体成功，零报错。**

断链位置清晰：

```
K-8 结构（label 无 for、无 placeholder）
  → visibleText 提取六档全空 → null
  → T-84 的语义断言无物可校
  → 直接执行
```

同时暴露二阶问题：**首跑 supervisedVerification 也只确认「位置能找到」，不校验语义**。用户看到的是「第 3 步成功」，看不到「这一步选中的是哪个选项」。

### 1.2 目标环境的会话形态已确认

| 事实 | 来源 | 影响 |
|---|---|---|
| 门户 cookie 是**持久型**，关浏览器后仍存活约 **4 小时**（过期时间随机，取保守值 4h） | 项目方实测 | Mock 默认应改为 persistent；session 模式保留为可选形态 |
| 子系统会话短得多，过期后可经门户静默重建，实测 **3.3 秒无感恢复** | GLM C.4 | 「门户会话是真正生命线」的设计成立 |
| 推荐用法：**用户自行登录一次，浏览器保持常驻，多开标签页操作，不反复关闭** | 项目方 | 会话常驻进程从"可选策略"升为**推荐主入口** |

### 1.3 会话常驻路径当前被堵死

cookie 派系统的四条入口全部不可用：

| 路径 | 状态 | 性质 |
|---|---|---|
| record 直启 | 卡死 >7min | bug（T-99 修） |
| **外部预种子 + record** | **租约强制接管、关闭种子浏览器、cookie 蒸发** | **设计问题（T-100 修）** |
| session-daemon | 同源异常崩溃 | bug（T-99 修） |
| CDP attach + record | IIFE 注入自检失败（4/5 全局缺失） | bug（T-100 修） |

**第二条是设计问题不是 bug**：即使修完其余三条，租约机制仍会关掉外部登录的浏览器。而按 §1.2 的推荐用法，「外部登录一次 + DSH 附着」是刚需——用户不可能每录一个技能就按一次指纹。

## 2. T-97 · 语义提取链扩展与控件属性断言【P0】

### 2.1 问题

当前 `visibleText` 提取优先级（六档）：

```
① accessible name
② 关联 <label> 的文本（需 for 关联）
③ aria-label / aria-labelledby
④ placeholder
⑤ title
⑥ 元素自身可见文本
```

对以下结构六档全空：

```html
<input type="radio" name="urgency" value="URGENT">
<span>紧急</span>          <!-- label 无 for -->
```

但该元素身上明明有可用语义：

| 来源 | 值 | 性质 |
|---|---|---|
| `element.value` | `URGENT` | HTML 标准属性 |
| `element.name` | `urgency` | HTML 标准属性 |
| 相邻文本节点 | `紧急` | DOM 结构 |

### 2.2 交付

**① 提取链扩展至八档**

```
① ~ ⑥ 保持不变

⑦ 控件语义（仅表单控件）：
   input[type=radio|checkbox] / select / option
   → 取 name + value 组合
   → visibleTextSource: 'control-semantics'

⑧ 相邻文本：
   a. 前一个兄弟节点的文本（跳过空白节点）
   b. 后一个兄弟节点的文本
   c. 最近的祖先 <label>（即使无 for 关联）的文本，剔除嵌套控件自身文本
   d. 同一 .el-form-item / fieldset 内的第一个文本节点（结构层面，不匹配框架类名）
   → 截断 40 字符
   → visibleTextSource: 'adjacent-text'

八档全空 → visibleText: null，visibleTextSource: 'none'
```

**⑧ 的实现约束**：只能依赖 DOM 结构关系（sibling / ancestor / label 标签），**禁止匹配任何框架类名**。`.el-form-item` 这类选择器不得出现在提取逻辑中。若需要"同一表单项内"的概念，用 `closest('label, fieldset, [role=group]')` 这类标准语义容器。

**② `recordedHint` 结构扩展**

```ts
export const RecordedHintSchema = z.object({
  action: z.enum([...]),
  visibleText: z.string().nullable(),
  visibleTextSource: z.enum([
    'accessible-name','label','aria','placeholder','title','text',
    'control-semantics','adjacent-text','none'      // 【新增两项】
  ]),
  /** 【新增】表单控件的标准属性语义，独立于 visibleText */
  controlSemantics: z.object({
    tagName: z.string(),
    type: z.string().nullable(),        // radio / checkbox / text / select-one ...
    name: z.string().nullable(),
    value: z.string().nullable(),
    checked: z.boolean().nullable(),    // radio/checkbox
  }).nullable(),
  tagName: z.string(),
  role: z.string().nullable(),
  matchCountAtRecord: z.number(),
});
```

**③ 回放前断言扩展**

LOW 步骤的执行前置断言，从「只比对 visibleText」扩展为：

```
LOW 步骤执行前，定位到唯一元素后：

1. 若 controlSemantics 存在（表单控件）：
   a. 比对 name         → 不一致即停
   b. 比对 value        → 不一致即停
   c. 比对 type         → 不一致即停
   【这三项是硬断言，优先于 visibleText】

2. 若 visibleText 非 null：
   归一化后比对（规则沿用 T-84 §3.3）→ 不一致即停

3. 若 controlSemantics 与 visibleText 均为空：
   → 该步骤标记为 unverifiable
   → 见 T-98 的处理
```

**注意**：`controlSemantics` 的断言**优先于** `visibleText`。因为 `value` 是机器语义，比可见文本更精确——文案可能被翻译或改写，`value` 通常不会。

**④ 报错信息**

```
✗ 执行中止：步骤 3（选择）

  录制时，此位置的控件是：urgency = URGENT（紧急）
  现在，此位置的控件是：  urgency = NORMAL（一般）

  该步骤使用位置型定位（getByRole('radio').nth(1)），
  页面结构变化后指向了不同的选项。

  为避免提交错误数据，已停止执行。
  该 Skill 已标记为需要重新录制。
```

**⑤ HIGH 步骤不受影响**

`controlSemantics` 录制时照常采集（用于诊断），但**HIGH 步骤不执行该断言**——沿用 T-84 的既有约定，避免假阳性。

## 3. T-98 · 首跑验证展示实际操作对象【P0 配套】

### 3.1 问题

T-79 设计的「LOW 步骤由用户首次监督确认」这道保险，对 B-1 类问题**无效**。

原因：首跑验证只确认「位置能找到、流程能跑通」。用户看到的是：

```
Skill 首次验证完成
请确认本次所有操作是否正确。
[确认正确] [发现错误]
```

他确认的是「流程走完了」，**看不到「第 3 步选中的是哪个选项」**。

### 3.2 交付

**① LOW 步骤执行时展示实际操作对象**

运行期间对每个 LOW 步骤输出：

```
步骤 3 · 选择故障等级
  定位方式：位置型（radio 第 2 个）
  录制时选中：紧急（urgency=URGENT）
  本次选中：  紧急（urgency=URGENT）        ✓ 一致
```

不一致时（理论上已被 T-97 拦截，此处为双保险）：

```
  录制时选中：紧急（urgency=URGENT）
  本次选中：  一般（urgency=NORMAL）        ✗ 不一致 —— 已中止
```

**② unverifiable 步骤强制逐步确认**

`controlSemantics` 与 `visibleText` 均为空的步骤（T-97 §2.2 第 3 种情况）：

```
运行前提示：
  此 Skill 含 1 个无法自动校验语义的步骤（步骤 7：点击）。
  该步骤仅能按位置定位，且无任何可比对的语义信息。
  首次验证时将在该步骤前暂停，请确认操作对象正确。

执行到该步骤时暂停：
  步骤 7 · 点击
    定位方式：位置型（button 第 4 个）
    即将点击的元素：
      标签：div
      文本：（空）
      属性：class="submitBtn_a1b2c_"
      位置：(x=420, y=680, w=88, h=32)
    [ 继续 ]  [ 中止 ]
```

**只在首跑验证时暂停**，`verified` 之后不再暂停（否则无法自动化）。

**③ 技能级 unverifiable 统计**

Recorder 完成界面与 `dsh replay --dry-run` 输出中显示：

```
共 9 个步骤
稳定定位：6
位置型定位：3
  其中可语义校验：2
  其中无法校验：1        ← 页面变化时无法自动检测错位
```

**④ 状态机联动**

`unverifiable` 步骤数 > 0 的技能：
- `requiresFirstRunVerification` 强制为 `true`
- `verifiedTtlDays` 缩短（建议 7 天，可配），因为它的风险高于普通 LOW

## 4. T-99 · 认证状态判定覆盖 302/HTML 形态【P1】

### 4.1 问题

`getAuthState` 在配置了 `sessionApi` 时走 API 分支并**直接 return**，而 `loginUrlPatterns` / `loginDomMarkers` 的页面级检测写在该 return 之后——**永远执行不到**（`packages/browser/src/auth.ts:8-40`）。

后果：门户 302 → 登录页 HTML 形态下，返回 `unknown`，然后抛「认证状态未知」异常。

实测影响：

| 路径 | 现象 |
|---|---|
| `ensureEntry` 直调 | 30.8 秒后抛异常，**横幅从未展示** |
| `dsh record` 冷启动 | 卡死 >7 分钟，无输出、无超时报错 |
| `session-daemon` | 同源异常崩溃，state 卡在 `starting` 不自愈 |

**这违背了项目的既定原则**：会话丢失时应当提示并等待用户重新登录。现在连「等」这一步都没走到。

### 4.2 交付

**① 判定链改为串联而非分支 return**

```
getAuthState(page, entry) 判定顺序（全部串联，任一确定即返回）：

1. sessionProbe（若配置）
   - 401                        → unauthenticated
   - 403                        → forbidden          【C13：403 ≠ 未登录】
   - 2xx + jsonPath 判定成功    → authenticated
   - 2xx 但响应无法解析或判定失败 → 继续第 2 步（不 return）
   - 请求异常                    → 继续第 2 步

2. 当前 URL 命中 loginUrlPatterns  → unauthenticated

3. DOM 命中 loginDomMarkers        → unauthenticated

4. 响应文本命中 loginDomMarkers（应对 fetch 跟随 302 后拿到登录页 HTML 的情况）
                                    → unauthenticated

5. 以上全部无法确定              → unknown
```

**关键**：第 1 步的失败不得终止判定链。

**② unknown 的处理改为等待而非抛异常**

```
ensureLoggedIn(page, entry) 收到 unknown 时：
  1. 刷新 probeUrl 重探一次
  2. 仍 unknown → 【不抛异常】
     - bringToFront()
     - 注入横幅：「DSH 无法确认登录状态，请在本窗口完成登录后继续」
     - 进入轮询等待（沿用现有 loginPoll / loginTotal）
  3. 轮询期间任一次探测得到 authenticated → 移除横幅，返回
  4. 超时 → 抛 LoginTimeoutError（明确的超时，不是「状态未知」）
```

**理由**：unknown 意味着「不确定」，而不确定时的安全默认是「当作未登录、请用户处理」，不是「崩溃」。这正是项目「不做越权、等用户重新登录」原则的落实。

**③ 统一两处探测逻辑**

Phase A 自查发现 `entry.ts:101,131` 与 `auth.ts:8-40` 是两条独立的探测路径，语义不一致：

- `entry.ts` 的 `response.json()` 失败 → catch → null → 判 unauthenticated
- `auth.ts` 的同类情况 → unknown → 抛异常

**要求合并为同一个实现**，两处调用同一函数。不允许存在两套语义。

**④ record / daemon 路径接入等待逻辑**

`dsh record` 冷启动与 `session-daemon` 必须走与 `ensureEntry` 直调相同的等待路径。当前 record 的等待路径不同导致死等无横幅——**统一到同一实现**。

**⑤ daemon 状态自愈**

- daemon 进程异常退出 → `.dsh/session-*.json` 中的 `state` 不得停留在 `starting`
- `dsh session status` 检测到进程不存在 → 清理残留 state 文件并如实报告

### 4.3 Mock 环境配套

**① 默认 cookie 模式改为 persistent**

项目方实测：门户 cookie 为持久型，关闭浏览器后约 **4 小时**内仍有效（过期时间随机，取保守值）。

```
apps/mock-portal 默认配置：
  PORTAL_COOKIE_MODE=persistent
  PORTAL_COOKIE_MAX_AGE=14400          # 4 小时
  SUB_COOKIE_MODE=session              # 子系统仍为会话型（真实形态）
  SUB_SESSION_TTL=300                  # 5 分钟
```

`session` 模式保留为可选开关（`PORTAL_COOKIE_MODE=session`），因为别的系统可能不同，且这是探测逻辑应覆盖的形态。

**② 模拟指纹登录按钮保留**

该按钮扮演「人按指纹」这一必须由人完成的环节，**不得改为自动登录**。

仅允许新增测试专用开关，用于自动化回归：

```
POST /portal/login?autoAuth=1     # 仅自动化测试使用，跳过按钮点击
```

人工验证流程必须走真实按钮点击路径。

## 5. T-100 · 会话常驻改造：租约附着 + attach 注入【P1 主路径】

### 5.1 问题

项目方确认的推荐用法：

> 用户自行登录一次，浏览器保持常驻，多开标签页操作，不反复关闭浏览器。

这要求每次 `record` / `replay` **附着到已开着的浏览器**。但当前：

| 问题 | 性质 |
|---|---|
| 租约机制检测到 profile 已有实例时**强制接管并关闭**，导致会话 cookie 蒸发 | **设计问题** |
| CDP attach 模式下 IIFE 注入自检失败（locator / snapshot / mutation / ancestorScope 四个全局缺失） | bug |

第一条 GLM 明确记为「产品设计本身封死此路」。**即使修完第二条，租约仍会关掉外部登录的浏览器。**

### 5.2 设计裁决

**租约机制改为：附着优先，接管需显式。**

```
launchDSHContext / record / replay 启动时：
  1. 检测目标 profileDir 是否已有活跃实例
     ├─ 无 → 正常启动（现有行为）
     └─ 有 → 尝试附着（默认行为，见下）
          ├─ 附着成功 → 复用该实例，不关闭
          └─ 附着失败 → 报错并提示，【不得强制接管】
                        「检测到 profile 已被其他进程使用但无法附着。
                          请关闭该实例后重试，或使用 --force-takeover
                          （注意：会关闭现有浏览器，会话 cookie 将丢失）」

  --force-takeover  显式开关，保留原有强制接管行为
```

**默认行为从「接管」改为「附着」是本任务的核心。**

### 5.3 交付

**① 附着能力**

- 常驻实例启动时暴露 CDP endpoint，写入 `.dsh/session-<entry>.json`
- 后续 `record` / `replay` 优先读取该文件并 `connectOverCDP` 附着
- 附着后**不得**调用任何会关闭浏览器的 API（`context.close()` / `browser.close()`）
- 附着方在退出时只断开连接，不影响常驻实例

**② attach 模式补注入（修 B-5）**

`connectOverCDP` 附着时，`addInitScript` 只对**之后新建的页面**生效，已存在的页面没有注入。

```
附着后必须：
  1. 对 context 调用 addInitScript（保证后续新页面有注入）
  2. 【新增】遍历现有所有 page，逐个执行注入脚本
  3. 执行注入自检（T-91 已加的四项检查）
  4. 任一缺失 → 报错，不得静默继续
```

**③ `dsh session` 命令族完善**

```bash
dsh session start --entry <id>
  # 启动常驻浏览器，执行 ensureEntry
  # 未登录时弹横幅等用户登录（依赖 T-99）
  # 登录成功后保持进程，写 endpoint 到 .dsh/session-<id>.json

dsh session status
  # 分层显示：
  #   门户会话      ✓ 有效（剩余约 3h12m）      ← 见 ④
  #   子系统会话    ✗ 已失效 → 可静默重建
  #   身份          sha256:a1b2c3d4
  #   浏览器进程    ✓ 存活 (pid 12345)
  #   CDP endpoint  ws://...

dsh session stop --entry <id>
```

**④ 会话剩余时长提醒**

门户 cookie 有效期约 4 小时且过期时间随机。用户需要知道什么时候该重新按指纹。

```
entry 配置新增：
  sessionHolding:
    expectedPortalTtlMs: 14400000      # 4 小时，保守值
    warnBeforeExpiryMs: 1800000        # 提前 30 分钟提醒
```

`dsh session status` 与 daemon 定期巡检时：

```
剩余 > warnBefore        → 正常显示
剩余 ≤ warnBefore        → 输出提醒：
                            「门户会话预计将在约 28 分钟后过期，
                              建议在开始长流程前重新认证。」
剩余 ≤ 0 或探测失败      → 「门户会话已失效，请重新登录」
```

**说明**：`expectedPortalTtlMs` 是**估算值**，用于提醒而非判定。实际是否有效**始终以 sessionProbe 探测为准**。不得因为估算未到期就跳过探测。

**⑤ record / replay 的会话来源优先级**

```
1. 存在 .dsh/session-<entry>.json 且进程存活 → 附着（推荐路径）
2. 不存在 → 自行启动 persistent context（现有行为）
3. 存在但进程已死 → 清理 state 文件，走第 2 条
```

### 5.4 文档要求

在 README 与使用文档中，把会话常驻写成**标准流程**而非可选项：

```markdown
## 标准使用流程

1. 每天开始工作时执行一次：
   dsh session start --entry <你的系统>
   在弹出的浏览器中完成登录（门户认证 / 指纹仪）

2. 之后所有录制与回放都附着到这个浏览器：
   dsh record --entry <系统> ...
   dsh replay skills/xxx.yaml

3. ⚠️ 使用期间请勿关闭该浏览器窗口
   需要同时操作多个页面时，请在同一浏览器中新开标签页。
   反复关闭重开会导致会话丢失，需要重新认证。

4. 门户会话约 4 小时过期，届时会提示重新登录。
```

**「请勿关闭浏览器」这一条不是建议，是使用前提**，必须写清楚原因（子系统会话靠门户静默重建，浏览器常驻才能无感）。

## 6. T-101 · CDP Cookie 证据采集与 pattern 语法契约

### 6.1 CDP Cookie 采集（修 B-2）

**问题**：`probeSessionType` 只订阅 CDP 的 `Network.requestWillBeSent` 主事件，而 **Cookie 头在 `Network.requestWillBeSentExtraInfo` 中**。

结果：cookie 派系统探测恒为 `sessionType: unknown` / `network: ✗`。与登录状态、401 形态均无关（两种 authFailMode 结果相同已佐证）。

**交付**：

```
probeSessionType 同时订阅：
  Network.requestWillBeSent            → 取 URL、method、非 Cookie 头
  Network.requestWillBeSentExtraInfo   → 取 Cookie 头【新增】
  按 requestId 关联两个事件

判定：
  有 Authorization，无 Cookie   → bearer
  无 Authorization，有 Cookie   → cookie
  两者都有                      → mixed
  两者都无                      → unknown（并说明未捕获到任何凭证证据）
```

同时补充 `cookieKind` 探测（T-92 已要求，此处确认）：读取落地后的 cookie，检查是否存在 `Expires` / `Max-Age`。

**验收**：

| # | 项 | 期望 |
|---|---|---|
| V-101-1 | cookie 派探测 | mock-portal 已登录后 `dsh doctor --probe-entry` → `sessionType: cookie`，`network: true` |
| V-101-2 | cookieKind 探测 | persistent 模式 → `cookieKind: persistent`；session 模式 → `cookieKind: session` |
| V-101-3 | bearer 派回归 | 真实 OA 探测结果不变 |
| V-101-4 | mixed 场景 | 构造同时带 Cookie 与 Authorization 的请求 → 判定 `mixed` |

## 7. T-102 · 跳转型提交支持

### 7.1 问题

老系统的标准形态是 SSR 表单提交后 302 跳列表页（K-10）。但：

**① 页内 fetch 拿不到 302 终态**

`redirect: 'manual'` 下响应是 opaque——status、body 均不可读。后果：

- `assertions` 中的 `httpStatus` 判不了
- `outcome` 落到 `outcome_unknown`
- 必须走 postcondition 才能确认

**这不是 bug，是 fetch 的规范行为。**

**② 录制侧在 302 跳转时崩溃**

GLM 实测两次复现：`session.js:44` 的 `__DSH_MUTATION__.end` 在导航中抛错，进程退出，**partial 全丢，但业务提交已落库**（records+1 而无 record.json）。

T-95 已覆盖导航竞态加固，但**未针对「提交后 302」这一具体场景**。

### 7.2 交付

**① 录制侧：302 提交场景专项加固**

在 T-95 的基础上追加：

```
检测到 form submit 或 mutating 请求后紧跟 302 时：
  1. 立即冻结并落盘当前 session（不等 settleNavigation）
  2. 再执行 settleNavigation
  3. 导航稳定后继续录制（页面已换，scope 全部失效）
  4. 在 record 中标记：
     { type: 'navigation-after-submit', atActionIdx, from, to }
```

**关键**：**先落盘再等导航**。因为副作用已经发生，此时崩溃的代价最大。

**② 分析器：识别跳转型提交**

```
若某个 mutating 步骤后紧跟 navigation-after-submit 标记：
  - 标记 step.expectsRedirect = true
  - 该步骤的 assertions 中【不生成】httpStatus 断言（拿不到）
  - 强制推断 postcondition（从跳转目标页或其数据接口）
  - 若无法推断 postcondition → 生成 TODO 并说明原因
```

**③ Schema 校验：跳转型提交强制 postcondition**

```ts
// parseSkill 新增校验
若某 step 满足：
   riskLevel ∈ {write, critical}
   且 expectsRedirect === true
   且 skill.postcondition 与 step.postcondition 均缺失
→ 抛 SchemaViolationError：
  「步骤 s5 是跳转型提交，响应状态不可读，
    必须配置 postcondition 才能确认业务结果。
    建议：GET <跳转目标的数据接口>，按业务标识匹配。」
```

**④ 回放侧：expectsRedirect 的 outcome 处理**

```
expectsRedirect === true 的步骤：
  1. fetch 返回 opaque（status 不可读）
     → 【不判为失败】
     → outcome 暂定 outcome_unknown
  2. 立即执行 postcondition
     ├─ 命中 → outcome 改写 confirmed_success
     ├─ 未命中 → outcome 改写 confirmed_failure
     └─ postcondition 请求失败 → 保持 outcome_unknown → 中止
  3. 记录 outcomeResolvedBy: 'postcondition'
```

**⑤ UI 通道的等价处理**

若该步骤走 UI 通道（点提交按钮触发 302），同样：
- 先 `settleNavigation`
- 再执行 postcondition 确认
- 不依赖页面上的成功提示文本（可能因改版消失）

### 7.3 验收

| # | 项 | 期望 |
|---|---|---|
| V-102-1 | 302 录制不崩 | mock-legacy-sys 完整录制（含提交 → 302 → 列表页）→ **进程不退出，record.json 完整** |

## 9. 注意事项

### 9.1 P0 的修法是补齐不是封堵

GLM 建议「visibleText=null 的 LOW 不可发布」。**本轮不采纳这个方案**，改为补齐提取链（T-97）。

原因：K-8 那个 radio 身上明明有 `name="urgency" value="URGENT"` 这样精确的机器语义，直接封堵等于放弃一个可用信号，还会把大量正常控件也堵死。

**只有八档全空的元素**（纯图标 div 按钮那种）才落到 unverifiable，由 T-98 的强制逐步确认兜底。

### 9.2 controlSemantics 优先于 visibleText

`value` 是机器语义，比可见文本更精确——文案可能被翻译、改写、加空格，`value` 通常不会。

所以断言顺序是：**先比 `name`/`value`/`type`，再比 `visibleText`**。

### 9.3 unknown 的安全默认是「等用户」不是「崩溃」

T-99 的核心变更是把 `unknown` 从抛异常改为进入等待。

这符合项目一贯原则：**会话丢失时提示并等待用户重新登录，不做任何越权尝试**。现在的问题不是越权，是连「等」都没走到。

### 9.4 附着优先是设计变更不是 bug 修复

T-100 把租约默认行为从「接管」改为「附着」，这是一个**设计裁决**，不是修 bug。

依据：项目方确认的推荐用法是「登录一次、浏览器常驻、多开标签页」。默认接管会关掉用户手动登录的浏览器，与该用法直接冲突。

`--force-takeover` 保留原行为，供确实需要干净环境的场景使用。

### 9.5 会话时长是提醒不是判定

`expectedPortalTtlMs: 4 小时` 是估算值（实测过期时间随机）。

**它只用于提前提醒用户，绝不用于判定会话是否有效。** 实际有效性始终以 `sessionProbe` 探测为准。不得出现「估算未到期所以跳过探测」这类优化。

### 9.6 不要把困难从测试环境删掉

已经踩过三次：静态 id、cookie 加 Max-Age、以及这次差点要改的模拟指纹按钮。

**本轮明确**：
- 模拟指纹按钮保留（人工路径必须点击）
- 子系统 cookie 保持 session 型（真实形态）
- K-8 的无 for 无 placeholder 结构保留（它正是 T-97 要覆盖的目标）

只有门户 cookie 从 session 改为 persistent，**因为那是项目方实测的真实形态**，不是为了让测试变简单。

## 10. 一句话总结

> 上一轮修的是「进不去」，本轮修的是「进去了但会静默出错」和「进去一次就得重新进」。
> T-97 是核心：`radio value=URGENT` 漂移成 `NORMAL` 却回放成功，这是整个项目一直在防的静默错单第一次被完整复现——修法是补齐语义提取，不是封堵功能。
> T-100 是主路径：用户按一次指纹、浏览器开着用一天，这个用法现在被租约机制封死了，必须改成附着优先。
