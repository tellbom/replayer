# 2. T-96 已完成实现的补充边界

T-96 的录制期 `actionIdx` / activeAction 属于**强 request ownership candidate**，但不得被解释为：

> 请求中的所有字段都来自该 action。

必须始终区分：

```text
Request ownership
    ≠
Field provenance
```

即使某请求带 `actionIdx`：

- 也必须逐 leaf 做 provenance；
- 无来源 leaf 不得自动参数化；
- 无来源时继续走 `TODO_UNRESOLVED`；
- 不得因为 actionIdx 存在而提高所有字段置信度。

建议补一条回归：

```text
用户正在输入
    +
同一时间发生无关后台请求

即使后台请求误带 actionIdx，
其无关 query/body/header leaf 也不得被参数化。
```

# 3. T-103 补充裁决

## 3.1 T-103 主方向批准

保留主文档核心：

```text
navigation
    ↓
settle
    ↓
从当前页面实例提取值
    ↓
ctx.vars
    ↓
后续 request 使用
```

继续禁止：

```text
分析器凭字段名生成录制中不存在的独立 GET
```

继续保留 C26：

> 页面 DOM 值若具有页面实例作用域，则提取必须发生在产生该实例的最后一次 navigation 之后、使用该值的请求之前。

---

## 3.2 删除 `untouched = immutable` 规则

主文档中：

```text
“录制中从未出现在任何用户动作 target 中的元素”
```

不得直接视为页面实例作用域值。

原因：

```text
用户没操作
    ≠
不可编辑
    ≠
页面生成动态值
    ≠
应该自动提取
```

因此 T-103 不得出现：

```ts
if (!wasUserTarget(element)) {
  kind = 'untouched';
}
```

并据此自动生成 provenance。

---

## 3.3 PageSnapshot 候选范围收窄

优先候选：

```text
1. input[type=hidden]
2. readonly 且具有 value 的标准表单控件
3. 必要的 meta/content
4. 其它能被证明由当前页面实例生成，
   且其值后来实际进入 request 的 DOM value
```

`disabled`：

- 可以作为 candidate；
- 不得仅因 disabled 就直接认定为提交依赖；
- 标准 HTML form 不提交 disabled control，必须有额外数据流证据。

---

## 3.4 优先记录“被消费的页面值”，不要全页面持久化

推荐：

```text
页面加载
    ↓
建立 page-scoped candidate pool
    ↓
后续 network request 消费 value X
    ↓
才将 X 对应的 provenance 固化进最终 record
```

不推荐：

```text
每次 navigation
    ↓
把页面全部 hidden/readonly/meta/untouched 大量落盘
```

目标：

- 减少 record 体积；
- 减少敏感信息采集面；
- 减少短值 / 重复值假匹配。

所有真正落盘的数据仍必须经过现有 sanitize。

---

## 3.5 PageSnapshot 不得另造独立因果体系

如果 T-96 已存在：

```text
actionIdx
activeAction
request causality
```

T-103 应复用这一因果体系。

不得形成：

```text
T-96 一套 interaction/action identity
T-103 再造一套独立 ownership identity
analyzer 第三套 owner identity
```

如果 schema 必须增加页面身份，建议概念为：

```text
pageInstanceId
causeRef / actionIdx
```

最终由 analyzer 映射到 Skill step。

# 4. C25 补充修订

原意保留，但“每个请求必须直接属于一个用户动作”过严。

C25 最终解释为：

> 每一个被显式纳入回放的网络请求，必须能够追溯到录制期间观察到的因果链。该因果链最终根植于用户 interaction、其导致的 navigation / page lifecycle，或此前已确认的 response dependency。分析器不得凭字段名、端点名或值猜测生成录制中不存在的独立请求。

允许：

```text
用户 click
  → navigation
  → 页面初始化 request A
  → response A
  → request B
```

只要 B 能沿已录制因果链回溯。

禁止：

```text
看到某个 hidden field 名
  → analyzer 自行猜一个 GET
  → 回放时发出录制中不存在的独立 request
```

# 5. T-104 补充裁决

## 5.1 Analyzer 容错主方向批准

继续执行：

```text
合法 RecordSession
+
单动作 / 单字段异常
    ↓
TODO_UNRESOLVED / _notes
    ↓
draft 继续产出
```

只有整个输入不是合法 RecordSession 时，才允许顶层失败。

---

## 5.2 高熵启发只能是 suspected

必须拆为两级：

```text
A. 跨录制确认属性变化
   → confirmed unstable

B. 单次录制仅检测到高熵字符
   → suspected unstable
```

`confirmed unstable`：

- 可排除参数化；
- 可降低 / 禁止其作为定位主依据。

`suspected unstable`：

- 只能降低 confidence；
- 写入 `_notes`；
- 不得单凭高熵直接删除参数来源；
- 不得单凭高熵直接使 locator 失效。

禁止：

```ts
if (looksHighEntropy(value)) {
  return definitelyUnstable;
}
```

# 6. T-105 补充裁决

## 6.1 先定级仍然保留

T-105 开始时先回答：

```text
两个不同 source 被错误合并为一个参数后，
是否存在能够真正走到提交且服务端接受的路径？
```

若存在：

```text
P0：静默错误
```

必须暂停并优先修复 T-105。

---

## 6.2 C28 改为 Source Lineage Identity

废止字面规则：

```text
参数与 DOM 控件实例一一对应
```

替换为：

> 参数身份来自 source lineage，而不是值。

正式规则：

```text
1. 不得仅因值相同而合并参数
2. 不得仅因值相似而合并参数
3. 不得因参数命名冲突而复用已有参数
4. 默认不同 source lineage 保持独立
5. 只有存在可靠同源证据或人工显式声明时才允许共享
```

同一个逻辑参数可以合法跨：

- SPA rerender；
- wizard 多页面；
- 重复确认控件；
- 同源参数在不同 UI instance 再次出现。

---

## 6.3 Source identity 证据优先级

推荐使用：

```text
interaction/action provenance
+ standard DOM semantics
    name
    type
    role
    associated label
    form scope
+ stable locator fingerprint
```

容器内位置：

```text
只能作为 tie-breaker
```

不得把：

```text
locator + nth
```

作为参数身份的主要真相。

若无法证明两个 source 同源：

> 宁可生成两个独立参数，也不要自动合并。

---

## 6.4 expectsRedirect 改为因果规则

废止：

```text
“后面紧跟一次 navigation”
```

作为 correctness 判据。

替换为：

> `expectsRedirect` 只有在录制证据表明该 navigation 由该 mutating step / form-submit interaction 因果触发时才能设置。

优先复用：

- navigation-after-submit；
- T-96 action/network causality；
- 已记录的 navigation lifecycle。

不得仅依据时间距离。

# 8. T-107 重写要求【不得按旧版执行】

旧版以下判据作废：

```text
sessionType != cookie
+
loginUrlPatterns 非空
    ↓
“跳转式认证系统”
```

旧版以下默认行为作废：

```text
无常驻 session
    ↓
默认拒绝 cold start
```

原因：

```text
认证配置形态
    ≠
实际 navigation 行为
```

---

## 8.1 T-107 新任务名称

```text
T-107 · Cold-start Navigation Stabilization
```

---

## 8.2 通用运行时方案

```text
cold launch
    ↓
initial navigation
    ↓
观察 navigation / redirect lifecycle
    ↓
等待达到稳定态
    ↓
再执行 landing / sessionProbe
```

“稳定态”必须基于浏览器实际观察，而不是认证产品或 sessionType 分类。

---

## 8.3 行为原则

- bearer 可以不跳转；
- cookie 系统一样可能连续多次 302；
- mixed 不能推导一定有复杂认证；
- `loginUrlPatterns` 只能作为登录页面证据，不是“重定向系统分类器”。

因此 packages 核心不得出现：

```ts
if (sessionType === 'bearer' && loginUrlPatterns.length > 0) {
  rejectColdStart();
}
```

---

## 8.4 无法稳定时

如果 navigation lifecycle 在既定通用稳定策略下仍无法收敛：

```text
→ 明确失败
→ 输出观察到的 navigation 状态
→ 建议用户使用 persistent / attached session
```

建议常驻 session 是 fallback / UX 提示，不是认证分类结果。

---

## 8.5 T-107 验收改写

至少：

```text
V-107-1
无 redirect 的 bearer/cookie/mixed 页面
→ cold start 不误阻断

V-107-2
存在多跳 navigation/redirect
→ 等待稳定后继续

V-107-3
多跳结束后
→ landing/sessionProbe 才执行

V-107-4
无法稳定
→ 明确失败，不假装 authenticated

V-107-5
有 attached persistent session
→ 行为不退化

V-107-6
packages/* 不得按认证产品名或 sessionType
决定是否允许 cold start
```

# 9. T-108 补充裁决

## 9.1 DOM enum source 批准

允许：

```text
原生 select.options
标准 role=option
明确属于该控件的 DOM option set
    ↓
enum candidate
```

---

## 9.2 Response → enumMap 必须满足更强证据

不能仅凭：

```text
response 到达
    ↓
options 从空变非空
```

就直接永久固化为静态 enumMap。

至少需要证明：

```text
1. response 与目标控件 DOM mutation 有因果关系
2. response leaf 与 option label/value 有字段级对应
3. option set 不依赖其它可变参数
```

满足三项：

```text
→ 可生成 static enumMap
```

无法证明第 3 项：

```text
→ dynamic/contextual enum
→ TODO / dependency
→ 不静态固化
```

典型反例：

```text
country=CN
    → city options = 北京/上海

country=US
    → city options = NYC/SF
```

不能把 CN 录制时看到的城市永久写成该参数全部 enumMap。

---

## 9.3 sanitize 规则

不得把所有敏感字段模式都移出 core。

Core 必须保留真正通用的安全默认，例如：

```text
password
passwd
authorization
cookie
access_token
refresh_token
token
secret
apiKey
```

支持：

```text
coreGenericSensitivePatterns
+
entryAdditionalSensitivePatterns
```

具体 OA / fixture / 业务专用字段：

```text
不得作为 core correctness 或业务规则
```

如果确需额外脱敏：

```text
放 entryAdditionalSensitivePatterns
```
